|---|---|
| Extensions | `.iso` |
| Signature | `43 44 30 30 31` ("CD001") at offset 32769 (byte 1 of sector 16) |
| Arcana support | list, extract (Joliet and Rock Ridge names, multi-extent files, zisofs) |
| Main classes | `be.stef.arcana.formats.iso.IsoReader`, `be.stef.arcana.formats.iso.IsoDirectoryRecord`, `be.stef.arcana.formats.iso.RockRidgeParser`, `be.stef.arcana.formats.iso.IsoConstants`, `be.stef.arcana.extractor.IsoExtractor` |

## Overview

ISO 9660 (also published as ECMA-119) is the file system of CD-ROMs, defined
in 1988. The plain format only allows short upper-case names (8.3 at level 1)
and 8 directory levels. Two extensions are almost always present on modern
images: Joliet (Microsoft, 1995), a second directory tree with UCS-2 names,
and Rock Ridge (IEEE P1282, built on the SUSP framework of IEEE P1281), which
adds Unix names, modes, links and more in the "system use" area of each
directory record of the primary tree. ISO images are still the usual form of
Linux distributions, rescue media and software downloads.

The samples were made with genisoimage (`test/tools/make-samples.sh`):
`joliet-rr.iso` with `-J -R`, `level1.iso` with no extension (names shown as
`README.TXT`, `EMPTY_DI/`...).

## Detection

- `ArchiveDetector.detectByMagic` runs first on the first 264 bytes. If it
  finds nothing, `discFormat` checks the volume descriptors: UDF first
  (`isUdf`, "NSR02" / "NSR03" in sectors 16 to 31), then ISO 9660
  (`isIso9660`: "CD001" at offset 32769, file of at least 32774 bytes).
  An image that also carries UDF (a "bridge" disc, such as most DVDs and
  `udf-bridge.iso`) is therefore handled by the UDF reader.
- Without these signatures, the `.iso` extension selects `ISO`.
- Because the magic test comes first, an image whose system area (the first
  32 KiB, free for boot code) starts with another signature is taken as that
  format. Verified: `level1.iso` with "MZ" written at offset 0 is detected as
  a self-extracting executable and fails with "No archive found". `-f iso`
  forces the ISO reader (it also reads the ISO 9660 side of a bridge disc).
- `IsoReader` reads the descriptors from sector 16 on and fails with
  "Not a valid ISO 9660 image (missing CD001 identifier at sector 16)" or
  "No primary volume descriptor found in ISO image".

## Structure

The image is a sequence of 2048-byte sectors. Sectors 0 to 15 are the system
area (ignored). From sector 16 on, one volume descriptor per sector, until
the set terminator (type 255); `IsoReader.readVolumeDescriptors` stops there,
at the first sector without "CD001" (once a primary descriptor was found) or
after sector 80 (65 descriptors). Numbers are stored twice ("both-endian"); Arcana reads
the little-endian half.

| Offset | Size | Field | Notes |
|---|---|---|---|
| 0 | 1 | type | 0 boot record, 1 primary, 2 supplementary, 3 partition, 255 terminator |
| 1 | 5 | identifier | "CD001" |
| 6 | 1 | version | ignored |
| 88 | 32 | escape sequences | supplementary only: `%/@`, `%/C` or `%/E` mark Joliet levels 1-3 |
| 128 | 4 | logical block size | ignored, 2048 is assumed |
| 140 | 16 | path table locations | ignored |
| 156 | 34 | root directory record | used for type 1 and for a Joliet type 2 |

Only types 1 and 2 are used. The path tables (a flat list of all directories,
in L and M byte order) are not read: the tree is walked from the root
directory record through the directory extents.

A directory is an extent made of directory records, which never cross a
sector boundary; a record length of 0 means "skip to the next sector".
Directory record (`IsoDirectoryRecord.parse`):

| Offset | Size | Field | Notes |
|---|---|---|---|
| 0 | 1 | record length | 0: end of records in this sector |
| 1 | 1 | extended attribute length | in blocks, added to the extent location |
| 2 | 8 | extent location | sector number (both-endian) |
| 10 | 8 | data length | bytes (both-endian) |
| 18 | 7 | recording date | year-1900, month, day, hour, minute, second, GMT offset in 15 min |
| 25 | 1 | flags | 0x01 hidden, 0x02 directory, 0x04 associated, 0x80 not the last extent |
| 26 | 2 | interleave unit, gap | ignored |
| 28 | 4 | volume sequence number | ignored |
| 32 | 1 | identifier length | |
| 33 | var | identifier | 0x00 ".", 0x01 "..", else `NAME.EXT;1` |
| var | var | system use area | after a pad byte when the identifier length is even |

### Rock Ridge (SUSP entries)

The system use area holds entries of the form signature (2 bytes), length
(1), version (1), data. `RockRidgeParser` reads:

| Entry | Use in Arcana |
|---|---|
| `NM` | alternate name: flags at offset 4, name bytes from offset 5, decoded as UTF-8; fragments of several `NM` entries are concatenated; "." and ".." forms are ignored |
| `CE` | continuation area: sector (offset 4), offset in it (12), length (20); followed when the length is below 8192, up to 8 levels |
| `ST` | end of the entries |
| `ZF` | zisofs compression, see below (`RockRidgeParser.findEntry`) |
| `SP`, `RR` | only used to detect Rock Ridge |

`PX` (modes), `TF` (times), `SL` (symbolic links), `PN` (devices) and the
relocation entries `CL` / `PL` / `RE` are not interpreted.

## Compression and encryption

ISO 9660 has no compression or encryption. Arcana decodes zisofs, the
transparent compression of Linux (`mkzftree`, xorriso
`-set_filter_r --zisofs`), marked by a Rock Ridge `ZF` entry:

| Offset | Size | Field | Notes |
|---|---|---|---|
| 4 | 2 | algorithm | must be "pz", otherwise "ISO: unsupported transparent compression 'xx' for NAME" |
| 8 | 4 | uncompressed size | reported as the file size |

The file data then starts with a 16-byte header (`IsoReader.copyZisofs`):
an 8-byte magic `37 E4 53 96 C9 DB D6 07`, the size (4 bytes), the header
size / 4 (1 byte) and log2 of the block size (1 byte, 15 to 17 accepted).
A table of (blocks + 1) little-endian 4-byte offsets follows; each block is
a zlib stream decoded with `java.util.zip.Inflater`, an empty block stands
for zeros. Verified: an image made by xorriso 1.5.6 with zisofs extracts
identical to the source files.

## Variants and versions

- Interchange levels 1 to 3: names are taken as stored, after removing the
  `;version` suffix and a trailing dot (`getIso9660Name`, US-ASCII).
- Multi-extent files (level 3, files of 4 GiB and more): consecutive records
  with flag 0x80 form one file; the lengths are added and the extents copied
  in order. Verified with a 4.5 GB file in an image made by
  `xorriso -as mkisofs -iso-level 3`: listed with its full size, extracted
  identical (`cmp`).
- Joliet: when a supplementary descriptor carries a Joliet escape sequence
  and the primary tree has no Rock Ridge, the Joliet tree is walked and names
  are decoded as UTF-16BE (`getJolietName`). Verified with
  `genisoimage -J -input-charset utf-8`: accented names are correct.
- Rock Ridge: `IsoReader.primaryHasRockRidge` looks at the records of the
  root directory for an `SP`, `RR` or `NM` entry. When found, the primary
  tree is walked even if Joliet is present, and each name is the `NM` name
  when there is one, else the ISO 9660 name. Verified with names of 204
  bytes (stored through a `CE` continuation area).
- El Torito (bootable CDs): the boot record descriptor is ignored. A boot
  catalog or boot image is only listed when the authoring tool also put it in
  the tree (xorriso writes `boot.catalog`).

## Limits

- Rock Ridge directory relocation is not followed. genisoimage `-R` moves
  directories deeper than 8 levels to `rr_moved/` and leaves a `CL`
  placeholder: Arcana lists `rr_moved/...` and writes the placeholder as an
  empty file (verified: `d1/.../d7/d8` becomes an empty file, the content
  is under `rr_moved/d8/`).
- Symbolic links are extracted as empty files (their target in `SL` is not
  read); hard links become separate copies. Hidden and associated files are
  listed and extracted like the others; several versions of one name are
  written to the same path.
- Modes, owners and times are not restored: `IsoExtractor` does not use the
  recording date, which only appears in the listing.
- `extract(InputStream, File)` throws "ISO 9660 requires random file
  access - use extract(File,File)." (`supportsStream()` is false).
- Logical block sizes other than 2048 and multi-session images (only the
  descriptors found from sector 16 are read) are not handled.
- No creation of ISO images.

## Implementation notes

- Large images: only the volume descriptors and the directory extents are
  read when listing. Extraction copies each file with
  `IsoReader.copyExtent` (2048-byte reads from a `RandomAccessFile` into a
  64 KiB `BufferedOutputStream`), so memory use does not depend on the file
  size. A 4.5 GB file extracted in about 11 seconds in the test above.
- Walk order: the entries of a directory are reported first, then each
  subdirectory is walked (`walkDirectory`); "." and ".." are skipped.
- `layouts` maps the first sector of every multi-extent or zisofs file to
  its extents; `copyFileData` uses it, other files are one plain extent.
- Paths go through `SafePathBuilder.buildSafePath` and output files through
  `ExtractionGuard.open` (size, ratio and free space limits).
- Robustness: there is no loop or depth guard in the directory walk, and
  directory sizes are not bounded (see the discrepancies below). Errors seen:
  a truncated image gives "Unexpected EOF while reading ISO file data" on
  extraction; an image cut inside the descriptors gives an `EOFException`
  without message ("Error: null").
