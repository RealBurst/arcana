## Overview

7z is the native format of 7-Zip, written by Igor Pavlov and published in
1999. It is a container of "folders": each folder is a small graph of coders
(compression methods and filters) that turns one or more packed streams into
one output stream, which may hold several files one after the other (solid
compression). All metadata (file names, sizes, CRCs, times) is in a header
at the end of the archive, usually itself compressed and optionally
encrypted. LZMA and LZMA2 are the usual methods; AES-256 is the only
encryption.

## Detection

- `ArchiveDetector.detectByMagic` returns `SEVEN_Z` for the 6-byte
  signature; the extension fallback maps `.7z` and `.cb7` to `SEVEN_Z`.
- The first volume of a split archive (`x.7z.001`) starts with the signature
  and is detected as 7z. Another volume (`x.7z.003`) has no signature;
  `Arcana.resolveFormat` then answers "Volume of a split 7z archive: open the
  first volume, x.7z.001".
- A 7z archive after an executable or another prefix (7-Zip SFX) is found by
  `SfxExtractor` (see [sfx-executables.md](sfx-executables.md)).
- `ArchiveAnalyzer` (command `i`) reports "7-Zip archive (format version
  0.NN)" from bytes 6 and 7.

## Structure

Numbers are little-endian. The archive is a 32-byte signature header, the
packed streams, and the header (`SevenZFile.readHeaders`):

| Offset | Size | Field | Notes |
|---|---|---|---|
| 0 | 6 | signature | `37 7A BC AF 27 1C` |
| 6 | 1 | major version | must be 0, else "Unsupported 7z version" |
| 7 | 1 | minor version | 7-Zip writes 4; Arcana writes 4 |
| 8 | 4 | start header CRC | CRC-32 of the next 20 bytes |
| 12 | 8 | next header offset | relative to offset 32 |
| 20 | 8 | next header size | |
| 28 | 4 | next header CRC | CRC-32 of the header bytes |

`readStartHeader` checks the CRC of the 20 bytes and that the header lies
inside the file; `initializeArchive` checks the CRC of the header itself
("NextHeader CRC-32 mismatch").

The header is a tree of properties, each introduced by a one-byte id
(`NID`) and closed by `kEnd` (0). Numbers inside it use the 7z variable
length encoding: the count of leading 1 bits of the first byte gives the
count of extra bytes (0 to 8). Main ids:

| Id | Name | Content |
|---|---|---|
| 0x01 | kHeader | plain header: main streams info, then files info |
| 0x17 | kEncodedHeader | streams info of a folder whose output is the real header (compressed, possibly encrypted) |
| 0x04 | kMainStreamsInfo | pack info + unpack info + substreams info |
| 0x06 | kPackInfo | pack position, count, sizes (kSize), optional CRCs |
| 0x07 | kUnpackInfo | folders (kFolder): coders, method ids, properties, bind pairs; output sizes (kCodersUnpackSize); optional folder CRCs |
| 0x08 | kSubStreamsInfo | number of files per folder, their sizes and CRCs |
| 0x05 | kFilesInfo | per-file properties below |
| 0x0E / 0x0F / 0x10 | kEmptyStream / kEmptyFile / kAnti | bit vectors: no data; empty file (not a directory); anti item |
| 0x11 | kName | names in UTF-16LE, each ended by two zero bytes |
| 0x12 / 0x13 / 0x14 | kCTime / kATime / kMTime | 64-bit Windows FILETIME values |
| 0x15 | kWinAttributes | 32-bit attributes |
| 0x19 | kDummy | padding, skipped |

An entry without stream is a directory unless kEmptyFile marks it as an
empty file. Unknown file properties are skipped; kStartPos and additional
streams are refused.

Before the header is parsed for real, `sanityCheckAndCollectStatistics`
walks it once to count folders, coders, streams and entries, and estimates
the memory the parsed header needs; above the memory limit it throws
`SevenZMemoryLimitException`.

## Compression and encryption

Coders decoded (`Coders.CODER_MAP`, method id in hex):

| Method | Id | Decoder |
|---|---|---|
| Copy | `00` | none |
| LZMA | `03 01 01` | `LZMADecoder` (XZ for Java `LZMAInputStream`) |
| LZMA2 | `21` | `LZMA2Decoder` (XZ for Java `LZMA2InputStream`), or `ParallelLZMA2InputStream` (see Implementation notes) |
| PPMd var. H | `03 04 01` | `Ppmd7Decoder` (properties: order, memory size) |
| BZip2 | `04 02 02` | `BZip2InputStream` |
| Deflate | `04 01 08` | `java.util.zip.Inflater` (raw) |
| Deflate64 | `04 01 09` | `Deflate64InputStream` (see [zip.md](zip.md)) |
| Delta | `03` | `DeltaDecoder` |
| BCJ x86, PPC, IA64, ARM, ARM-Thumb, SPARC | `03 03 01 03`, `03 03 02 05`, `03 03 04 01`, `03 03 05 01`, `03 03 07 01`, `03 03 08 05` | XZ for Java filters (`X86Options`, ...) |
| ARM64, RISC-V | `0A`, `0B` | XZ for Java filters, optional 4-byte start offset property |
| Swap2, Swap4 | `02 03 02`, `02 03 04` | `Coders.SwapDecoder` (byte order of 2- or 4-byte words reversed) |
| BCJ2 | `03 03 01 1B` | `Bcj2Decoder` (4 inputs: main, call, jump, range coder) |
| AES-256 + SHA-256 | `06 F1 07 01` | `AES256SHA256Decoder` |

`SevenZFile.resolveCoderOutput` walks the coder graph of a folder from its
final output back to the packed streams through the bind pairs, so chains of
any length work. Only BCJ2 may have several inputs; any other
multi-stream coder gives "Unsupported multi input/output stream coder".

AES-256 (`AES256SHA256Decoder`). The coder properties hold:

| Offset | Size | Field |
|---|---|---|
| 0 | 1 | bits 0-5: NumCyclesPower; bit 7: salt present; bit 6: IV present |
| 1 | 1 | high nibble: salt size - 1 (added to bit 7); low nibble: IV size - 1 (added to bit 6) |
| 2 | n | salt, then IV (zero-padded to 16 bytes) |

The key is SHA-256 over 2^NumCyclesPower repetitions of salt + password +
8-byte little-endian counter; the password is the UTF-16LE encoding of the
text (`SevenZExtractor` decodes the UTF-8 bytes of `-p` into a `String`
first). NumCyclesPower 0x3F means the key is salt + password copied as is.
As in 7-Zip, values from 25 to 62 are refused before any hashing
(`ArcanaUnsupportedFormatException` "7z AES key derivation with 2^N SHA-256
rounds is not supported", `AES256SHA256Decoder.MAX_NUM_CYCLES_POWER` = 24):
a crafted archive cannot make the key derivation run for hours. 7-Zip
writes 19 (2^19 rounds).
The data is AES-256 in CBC mode without padding (`AES/CBC/NoPadding`); the
size of the decrypted stream comes from the folder.

There is no password check value: a wrong password gives garbage that the
next coder rejects. On the samples, a wrong password reports "Compressed data
is corrupt". Without a password, `SevenZPasswordRequiredException` "Archive
is encrypted but no password was specified".

Header encryption (`-mhe` in 7-Zip): the kEncodedHeader folder contains an
AES coder; `readEncodedHeader` decodes it with the password, so even listing
needs `-p` (`encrypted-headers.7z`). With data-only encryption
(`encrypted.7z`), listing works without a password.

Creation, `SevenZCompressor` (`arcana c <source> out.7z [-l 0-9] [-p pw]`):

- one solid folder with LZMA2 (XZ for Java encoder, preset 0-9, default 6;
  dictionary 256 KiB at preset 0 up to 64 MiB at preset 9), encoded by
  several threads in independent LZMA2 blocks through
  `ParallelLZMA2OutputStream`;
- with `-p`: a second coder AES-256 (`SevenZAesOutputStream`),
  NumCyclesPower 19, random 16-byte salt and IV (`SecureRandom`), zero
  padding to 16 bytes;
- the header (kName, kMTime, kWinAttributes, kEmptyStream for directories,
  CRC-32 of every file) is compressed with LZMA2 into a kEncodedHeader but is
  **not** encrypted: file names stay visible without the password (checked
  with `7z l`);
- paths are relative to the parent of the source (a directory `src` is
  stored as `src/...`); version 0.04; directories are written after all files; the 32-byte start
  header is patched at the end. To an `OutputStream`, the archive is first
  built in a temporary file.
- Verified with 7-Zip 16.02: `7z t` accepts archives made with and without a
  password, including a password with accented letters.

## Variants and versions

- Solid and non-solid: `not-solid.7z` and `copy.7z` have 4 folders, the
  others 1. An archive made by 7-Zip with 2 files per solid block (`-ms=2f`)
  extracts correctly.
- Filters: `delta.7z` (Delta:4 + LZMA2). BCJ2 + 3 x LZMA and ARM + LZMA2
  archives made by 7-Zip 16.02 were extracted correctly while writing this
  page.
- Split archives: `MultiVolumeChannel` presents `x.7z.001`, `x.7z.002`, ...
  as one seekable file (7-Zip splits byte by byte). Verified with a 3-volume
  archive.
- Names are UTF-16LE: `names-utf8.7z` (accented and 120-character names)
  lists and extracts correctly.
- Samples by method: `copy.7z`, `lzma.7z`, `lzma2.7z`, `bzip2.7z`,
  `deflate.7z`, `ppmd.7z` (PPMd order 6, 1 MB), `delta.7z`, `encrypted.7z`
  and `encrypted-headers.7z` (LZMA2 + AES, NumCyclesPower 19).

## Limits

- Decoder memory is limited to 128 MiB (`SevenZExtractor`,
  `DEFAULT_MEMORY_LIMIT_KIB`); the limit can only be changed through the
  `SevenZExtractor(byte[], int)` constructor, not from the CLI. An LZMA2
  archive with a 192 MiB dictionary made by 7-Zip (`-md=256m` on 200 MB of
  data) fails with "Memory limit 131072 KiB exceeded (need 196712 KiB)".
- Not supported: Zstandard, Brotli, LZ4 and the other methods of 7-Zip
  forks; "Unsupported compression method [...]" is reported for unknown ids.
- Anti items (kAnti) are not treated specially: they come out as empty
  files or directories.
- Entries without a name (archive made from standard input with `7z a -si`)
  fail: listing gives "name must not be null" and extraction a
  `NullPointerException` from `SafePathBuilder`, because `SevenZExtractor`
  does not enable the default-name option of `SevenZFile`.
- Stream input is not supported (`supportsStream()` is false): "7z requires
  random file access".
- Times and attributes are listed (modification time) but not restored.
- The pack stream CRCs of kPackInfo are read but not checked; folder and file
  CRCs are.
- Header encryption is never written by `SevenZCompressor`; only LZMA2 is
  used for creation (no filters, no other method).
- AES key derivation: at most 2^24 SHA-256 rounds (NumCyclesPower 24, or
  0x3F for no hashing), like 7-Zip; `damaged/7z-aes-rounds.7z` (patched to
  30) fails at once.
- Common extraction limits apply through `ExtractionGuard`.

## Implementation notes

- `SevenZFile` and most of `formats/sevenz` are ported from Apache Commons
  Compress 1.28.0. Arcana additions: `Bcj2Decoder` and the coder-graph walk,
  `MultiVolumeChannel`, `PackedStreamInputStream` (packed streams are read
  from the file on demand instead of being loaded in memory), PPMd through
  `Ppmd7Decoder`, ARM64 / RISC-V / Swap filters, `getFolderIndexes` and the
  parallel paths.
- Integrity: CRC-32 of the start header, of the header, of each folder when
  present (`SevenZChecksumInputStream` over the folder) and of each file.
  `SevenZExtractor` also checks that each file has its declared size, because
  a damaged stream can end before the CRC is reached ("7z entry '...' is
  truncated").
- Parallel extraction (`SevenZExtractor.extractParallel`): with 2 folders or
  more, folders are decoded by several threads, each with its own
  `SevenZFile`; the memory budget per worker is the memory limit + 16 MiB. A
  name stored twice is decoded every time (solid stream) but written once,
  the last copy winning.
- Inside one folder, a plain LZMA2 folder made of independent blocks (7-Zip
  `-mmt`, Arcana) is decoded by several threads through
  `ParallelLZMA2InputStream.tryOpen`; other folders are decoded in a
  read-ahead thread (`ReadAheadInputStream`).
- Paths go through `SafePathBuilder.buildSafePath` (no `..` escape).
- Damaged archives: `SevenZRecovery` and `Lzma2SegmentRecovery`, see
  [recovery.md](recovery.md). The option of `SevenZFile` that scans for a
  lost end header (`setTryToRecoverBrokenArchives`) is off.
